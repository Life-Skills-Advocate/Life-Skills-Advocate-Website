Lead Magnet Request API

How a freebie form on lifeskillsadvocate.com hands a lead to Advocate360, and what the new hand-coded site has to send to reproduce what Thrive Leads does today.

For Edder Flores From Webster Munoz Verified against develop @ 2026-09-01

What this replaces

The mechanism behind every freebie form on the current WordPress site.

Today each Thrive Leads form has a webhook connection with a hardcoded asset ID — the 89 and 106 you saw in the form builder. On submit, WordPress posts the email plus that ID to Advocate360. Advocate360 is the router from there: it validates the asset, stores the lead, mints a one-off token, and tells Klaviyo to send the delivery email. The new site does the same POST; nothing downstream changes.

1
Visitor submits the formYour siteYou collect an email, optionally a first name, and you already know which asset the form is for.
2
POST to the lead magnet endpointYour siteOne JSON request with an X-API-Key header. This is the only call you make.
3
Advocate360 validates and recordsA360Confirms the asset exists and is actually giveaway-eligible, normalises the email to lowercase, generates a unique token, writes the request row. If the email already has an account, the asset also lands in that user's My Materials.
4
Klaviyo subscribes and sendsA360The profile is added to the list as a fresh opt-in (which clears any past unsubscribe), then the lead magnet event fires with the link.
5
Visitor opens the linkA360/lead/{token} — the splash page where they download the file and can create an account. Entirely ours; you do not build it.

Your job stops at step 2. Show a "check your email" confirmation on a 200 and you are done.

The endpoint

One route, one method, one header.

POST /api/lead-magnet/request
Production
https://advocate360.app/api/lead-magnet/request
Dev / staging
https://dev-app.lifeskillsadvocate.com/api/lead-magnet/request
Auth
X-API-Key: <key> — sent separately, never in the repo
Content type
application/json

Build against dev first. It is a full copy of the stack with its own database, so you can submit as many test leads as you like without touching real contacts. The two environments use different API keys.

Use advocate360.app, not the old host

The existing Thrive webhooks still point at app.lifeskillsadvocate.com and still work — page requests on that host redirect, but /api/* is deliberately never redirected so nothing breaks mid-migration. New code should use advocate360.app anyway.

Request body

Four fields. Two of them are the whole story.

FieldTypeRequiredNotes
emailstringYesValidated as a real address. Stored lowercase.
first_namestringNoPassed to Klaviyo for the email greeting. Send it when the form has the field.
resource_idintegerExactly oneUse for a resource (PDF, workbook, guide).
exercise_idintegerUse for an exercise or template.

Exactly one of resource_id or exercise_id. Sending neither is rejected; sending both is rejected. There is no type field — the field name you pick is the type.

Minimal request

POST /api/lead-magnet/request
Host: advocate360.app
Content-Type: application/json
X-API-Key: <your key>

{
  "email": "parent@example.com",
  "first_name": "Sam",
  "resource_id": 106
}

curl, to try it against dev

curl -X POST https://dev-app.lifeskillsadvocate.com/api/lead-magnet/request \
  -H "Content-Type: application/json" \
  -H "X-API-Key: $LEAD_MAGNET_API_KEY" \
  -d '{"email":"edder+test@example.com","first_name":"Edder","resource_id":106}'

Resource vs exercise

Same endpoint, same headers, same response. One field name changes — and the eligibility rules behind it differ.

Resource

A downloadable file — the PDFs, workbooks and guides in the resource library. This is what almost every current freebie form sends.

Advocate360 rejects it unless:

  • is_paid is false — a lead magnet can never give away something we sell
  • is_public is true — staff-only internal documents are not giveaway material
{
  "email": "parent@example.com",
  "first_name": "Sam",
  "resource_id": 106
}
Exercise

An exercise or template from the exercise library. Structurally identical to send — only the field name and the eligibility rules differ.

Advocate360 rejects it unless:

  • is_published is true — drafts cannot be handed out
  • is_gated is false — gated exercises are for signed-in users
{
  "email": "parent@example.com",
  "first_name": "Sam",
  "exercise_id": 42
}

Practically: your form component takes an asset type and an ID, and picks the key name from the type. One component covers both, which is the reuse you were after with React components.

The eligibility rules are the ones that bite in practice

The IDs are stable, but an asset's flags are edited in the admin area and nothing warns the website when one changes. If a form that worked yesterday starts returning 400, somebody almost certainly marked the asset paid, unpublished or gated — it is not a bug in your request.

Responses

What comes back, and what each failure actually means.

200 OK

{
  "success": true,
  "token": "Xk3nQ8vRt2mBpL7a",
  "link": "https://advocate360.app/lead/Xk3nQ8vRt2mBpL7a",
  "existing_user": false
}

You do not need to do anything with token or link — Klaviyo already has them and sends the email. existing_user tells you the address already has an Advocate360 account; the asset was also added to their library. If you ever want different confirmation copy for returning users, that is the flag to read.

StatusMeansWhat to do
200Lead recorded, email on its wayShow the confirmation message
401API key missing or wrongCheck the header name is exactly X-API-Key, and that you are using the key for that environment
404No asset with that IDWrong ID, or a dev ID used against production. The two databases do not share IDs.
400Asset exists but is not giveaway-eligibleRead the detail string — it names the reason (paid, internal, not published, gated)
422Body failed validationBoth IDs sent, neither sent, or the email is malformed
500Key not configured on the serverOurs, not yours — tell Webster

Every error returns a JSON body with a detail string. Log it; it names the exact cause.

This cannot be a browser fetch

The one thing to settle before you build the form component.

Posting this straight from client-side JavaScript will not work, and should not

On the call you described capturing the input fields and pushing to Advocate360 with JavaScript. That plan hits three walls, and the first two are hard stops:

  • CORS blocks it. The API only accepts browser requests from the Advocate360 hostnames. lifeskillsadvocate.com is deliberately not on that list — the integration was built as server-to-server and needs no origin.
  • The API key would be public. Anything in front-end JavaScript is readable by anyone who opens devtools. That key authorises freebie requests for any email address.
  • There is no rate limit on this endpoint, because until now only WordPress could reach it. A leaked key means anyone can send our files to any address, at any volume, from our domain.

The fix is small: post the form to a server-side route on the new site, and have that route add the X-API-Key and call Advocate360. Same-origin from the browser, so no CORS; the key stays in the host's environment variables. On Vercel or Netlify that is one serverless function.

This is also the point that decides your React-vs-static question in a way we did not discuss: whichever you pick, the site needs somewhere to run that one piece of server code. Worth confirming with Chris where the new site will be hosted before you build the form.

Where the IDs come from

And an honest answer on the automatic library idea.

Today: the Advocate360 admin area lists every resource and exercise with its ID, the same screen I shared on the call. Chris and I can pull you the current list of giveaway-eligible assets whenever you need it.

There is no public endpoint you can call to enumerate them. The resource and exercise listing endpoints both require a signed-in user, so a build step cannot fetch the catalogue as things stand.

So the library that auto-syncs IDs into the website — and the idea of a new freebie generating its own form — is real and buildable, but it is net new work on our side, not something you can wire up against what exists. We agreed to keep it out of the MVP; I will raise it as a ticket so it is on the board rather than living in a call recording.

Two things not to carry over

Assumptions in the current site's copy that are wrong.

Lead magnet links do not expire

If any page or email template you migrate says a download link expires — 30 days is the number that has floated around — drop that sentence rather than reproducing it. The links have no expiry, and we have already had one round of policy drafting misled by a stale comment in our own code. Publishing an expiry we do not enforce is a promise we would be breaking.

Stripe and HubSpot stay as redirects

Paid resources and the discovery-call buttons are plain outbound links to Stripe Checkout and the HubSpot scheduler. There is no API contract to rebuild there — keep them as links and they keep working.
